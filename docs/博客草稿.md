## 二、需求分析（有几个地方我一开始没看懂）

**1. -r 到底限制什么。** 题目里写的是“控制题目中数值（自然数、真分数和真分数分母）的范围”。
我一开始以为答案也要小于 r，那样 9×9 就不能出了。后来我按字面理解，把它当成“题目里出现的数”，
也就是每个操作数都小于 r，答案可以超过 r。为了保险我又加了个 `--strict-range` 开关，
打开之后每一步的中间结果也要求小于 r，这样两种理解都照顾到了。

**2. 除法的结果必须是真分数。** 我按最严格的写法做的：e1 ÷ e2 必须满足 0 < e1 < e2。
所以程序里不会出现 6 ÷ 3 = 2 这种整除的题，除法算出来永远是比 1 小的分数。

**3. 去重那条规则最绕。** 题目说 3+(2+1) 和 1+2+3 算重复，但是 1+2+3 和 3+2+1 不算重复。
我一开始想的是把一道题里所有的数排个序再比较，结果发现那样 1+2+3 和 3+2+1 也会被判成重复，
和题目说的不一样。想了挺久才转过弯：这道题只允许交换 + 和 × 左右两边的位置，不允许把括号拆开重新结合。
1+2+3 其实就是 (1+2)+3，交换一下就成了 3+(1+2)，再把括号里换一下就是 3+(2+1)，所以和第一个例子重复；
而 3+2+1 是 (3+2)+1，光靠交换变不成 3+(1+2)，所以不算重复。
想通这一点之后，去重就好写了（见第三节）。

## 三、程序是怎么写的

### 3.1 文件怎么分

```
Myapp.py              命令行入口，处理 -n / -r / -e / -a
arithmetic/
  fraction_utils.py   数字和文字互相转换（自然数、3/5、2'3/8）
  expression.py       表达式树：算结果、打印式子、算“指纹”用来查重
  parser.py           把题目文本读回成表达式（批改的时候要用）
  generator.py        出题和查重
  grader.py           判分，写 Grade.txt
  cli.py              参数检查、读写文件、给人看的提示
tests/                78 个测试
bench/                性能测试脚本、报告、效能分析图
tools/selfcheck.py    自己写的检查脚本，专门查一万道题合不合格
```

依赖关系很简单：`cli` 调用 `generator` 和 `grader`，这两个再调用 `expression` 和 `parser`，
最后都用到 `fraction_utils`。没有绕来绕去的互相调用。

表达式我用了两种节点：一种是一个数（叶子），一种是“左孩子 + 运算符 + 右孩子”。
这样正好对应作业里给的文法 e = n | e1 op e2 | (e)。所有计算都用 `fractions.Fraction`（Python 自带的分数），
不用小数，所以 1/6 + 1/8 一定等于 7/24，不会出现算出来是 0.2916666 这种。

### 3.2 出题：第一版不行，重写了一次

第一版的想法很直白：随机造一棵表达式树，造完整体检查一遍，如果哪里不符合要求（减出来是负数、
除法不是真分数），整棵树丢掉重新随机。写起来很快，但一跑就发现问题：造出来的大部分树都不合格，
全被丢掉了。更麻烦的是把范围调小（比如 -r 2）的时候，几乎造不出合格的题，程序像卡住了一样。

后来我改成从下往上建：先决定这道题用几个运算符，再一个个节点建起来。
关键在于，建到减法和除法的时候，我不让它“碰运气”：

* 减法的两个孩子在拼上去之前，先看看哪个大，把大的放被减数那边，这样一定不会减出负数；
* 除法的两个孩子，把小的那个放被除数那边，这样结果一定是真分数（两个数一样大的话就重抽）。

这两个小动作看起来不起眼，但效果很明显：原来每次尝试大概只有一半能成功，改完之后基本每次都能用上。
出题的大致过程是：

1. 随机决定用几个运算符（1 到 3 个）；
2. 从下往上建树，碰到减法和除法就按上面说的摆好两边；
3. 建好之后算一下“指纹”；
4. 如果指纹和之前出过的题重复，就丢掉重新来；不重复就留下；
5. 凑够 -n 指定的数量就停，同时写出两个文件。

还有一个小处理：为了避免出现 0+0、8×0 这种没意思的题，我在加减和乘法那里把“字面量 0”排除掉了
（0 还是可以出现在其他地方，比如 3−0）。

### 3.3 查重：给每道题算一个“指纹”

查重是这道题的关键。我的做法是：递归地处理表达式，碰到 + 和 × 就把左右两边按指纹的字典序排一下
（因为这两个可以交换），碰到 − 和 ÷ 就保持原来的顺序（不能交换）。
最后拼成一个字符串，比如 `+(+[1,2],3)` 这样。两道题的指纹一样，就认为是重复的。

这样 23 + 45 和 45 + 23 的指纹一样（重复），6 × 8 和 8 × 6 也一样；
1 + 2 + 3（也就是 (1+2)+3）的指纹是 `+(+[1,2],3)`，3 + (2 + 1) 也是这个指纹，所以判成重复；
而 3 + 2 + 1 是 (3+2)+1，指纹是 `+(+[2,3],1)`，和上面不同，所以不重复——正好和作业里的例子对上。

指纹就是个字符串，所以我直接把它扔进 Python 的 `set` 里，查重就是 O(1) 的查找，
不用两两比较（一万道题要是两两比就是几千万次比较，肯定慢）。

### 3.4 打印式子时括号怎么加

打印的时候括号不能多加也不能少加。我的规则是：

* 优先级比父节点低，必须加括号，比如 (1 + 2) × 3；
* 优先级和父节点一样、而且自己是右边的孩子，也必须加，比如 1 − (2 − 3)、6 ÷ (2 ÷ 3)；
* 优先级一样但是在左边就不用加，(1 + 2) + 3 直接写成 1 + 2 + 3 就行。

我写了一组测试专门验证这个：把打印出来的式子再读回程序里算一遍，结果和原来一样才算过。

### 3.5 判分

判分我没有拿答案文件当标准答案，而是**照着题目重新算一遍**，再和学生写的答案比。
比的时候比的是数值（都是分数），所以学生写 2/4、1'1/6、14/12 都算对。
读文件的时候也做了一些容错：题号前缀（`1. `、`（2）`）、行尾多余的等号、全角括号都当成正常情况处理，
文件是 GBK 编码的也能读。

## 四、效能分析

### 4.1 花了多少时间、怎么改的

性能这块大概花了 1.5 小时（写了对照用的旧算法、跑基准、画图、看热点函数）。

前面说过第一版的毛病是造废题。我用 cProfile 看了一下，确认时间确实都花在反复随机和反复丢弃上。
改成从下往上建之后，我又做了三件事：

1. 减法和除法在拼接的时候就摆好位置，不再整棵树作废；
2. 查重改成指纹 + `set`，避免两两比较；
3. 全程用分数，不碰小数，少了一堆容差判断。

还有一个体验上的问题：旧算法在题目空间不够的时候（比如 -r 2 想凑 800 道题）会一直转，
永远不告诉你“这个范围里根本造不出这么多题”。现在我用“连续很多次都没造出新题”来判断，
发现空间不够就停下来，在屏幕上提示把 -r 调大。

## 五、关键代码说明

这里挑四段比较关键的代码说一下思路（完整代码在 GitHub 上，地址见文章开头）。

**（1）括号规则**。上面 3.4 说的规则，代码就是一个函数：

```python
def _needs_parentheses(precedence: int, parent_precedence: int, is_right: bool) -> bool:
    # 优先级低 → 必须加括号；优先级相同而且在右边 → 也要加
    if precedence < parent_precedence:
        return True
    return precedence == parent_precedence and is_right
```

**（2）查重的指纹**。+ 和 × 才排序，− 和 ÷ 保持原样，这是整段代码里最要紧的一行判断：

```python
def canonical_key(self) -> str:
    left, right = self.left.canonical_key(), self.right.canonical_key()
    if self.op in COMMUTATIVE and right < left:   # COMMUTATIVE 里只有 + 和 ×
        left, right = right, left
    return f"{_OPERATOR_CODES[self.op]}[{left},{right}]"
```

**（3）减法、除法摆位置**。约束就在这一个地方解决掉：

```python
if operator == SUB:
    # 谁大谁当被减数，保证不会减出负数
    if left_value >= right_value:
        return Binary(SUB, left, right)
    return Binary(SUB, right, left)

if operator == DIV:
    # 小的当被除数，保证结果是真分数；两个数一样大就重抽
    if left_value <= 0 or right_value <= 0 or left_value == right_value:
        return None
    if left_value < right_value:
        return Binary(DIV, left, right)
    return Binary(DIV, right, left)
```

**（4）判分比数值**：

```python
expected = parse_exercise_line(line).evaluate()   # 照题目重新算一遍
if _clean_answer(answers[index - 1]) == expected:  # 两边都是分数，直接比
    result.correct.append(index)
else:
    result.wrong.append(index)
```

### 6.3 我还写了个自检脚本

单元测试是“我自己写的东西自己测”，我怕有盲区，所以又写了 `tools/selfcheck.py`，
换一条路验证：先把一万道题生成出来，然后照着**打印出来的文字**重新读一遍题目、重新算一遍答案，
再逐个节点看有没有违反作业要求。跑出来是这样：

```

[OK] 答案文本可解析且与题目一致：违例 0 处
```

### 6.4 为什么我觉得程序是对的

* 约束是**逐个节点**查的，一万道题大概三万个节点，一处违例都没有，不是随便抽几道看看；
* 检查用的是另一条路（先打印成文字，再读回来重算），不是复用生成时的那段代码，避免“自己检查自己”；
* 程序生成的答案再拿自己的判分功能去批，必须全对；
* 边界情况都试过：-r 只有 1、答案行数不够、题目写错、除以 0、GBK 文件、全角符号。

## 七、项目小结

**做得还可以的地方**

* 需求分析阶段多花了点时间，但很值。特别是去重那条规则，想清楚之后写代码快很多，
  而且不用回头改。
* “运算符不超过 3 个”我没用“生成完再检查”的办法，而是先决定用几个运算符再去建树，
  这样从结构上就不可能超。
* 作业里点名的几个例子（23+45 和 45+23、3+(2+1) 和 1+2+3、1+2+3 和 3+2+1、1/6+1/8=7/24）
  我都直接写成了测试用例，改代码的时候心里比较有底。

**走的弯路**

* 第一版的出题方法（随机造树再整体检查）在范围小的时候基本没法用，还差点让程序卡死。
  如果一开始就用 cProfile 看看哪里慢，能少返工一次。
* 我一开始只考虑了自己的程序生成的题目，没想过别人交上来的文件可能格式不一样
  （GBK 编码、带题号、全角括号）。后来是拿别人发我的一份文件试着批改才发现，才补上容错。
* 有个小坑：减号“−”和键盘上的“-”是两个不同的字符，在 Windows 上打印时出过问题，
  后来在程序开头把输出编码统一成 UTF-8 才好。

**一个人的感受**

没有搭档，最大的问题是没人逼你把想法讲清楚，写着写着容易自己说服自己。
我用了两个笨办法补：一是先写设计文档再写代码，写不清楚的地方就是没想明白；
二是每看到一条需求就先写一个会失败的测试，再写代码让它通过。
另外我还专门写了那个自检脚本，相当于换个身份再检查一遍自己的结果。

**给自己的建议**

* 下次遇到需求里前后例子看起来矛盾的情况，先把我的理解写下来再动手，不要写完了才发现理解错了；
* 继续坚持“一次提交只做一件事”，这次回头看 `git log` 能很快想起每一步改了什么；
* 优化性能之前先用工具量一下，不要凭感觉猜。

**还没做的**

* 图形界面没做（老师说可以选做）。命令行已经把要求的功能都覆盖了，做界面的话可以直接用现在的
  `generator` 和 `grader`，只是我没时间了。
* 题目难度是随机的，没做“按年级分难度”。
* 批改的时候如果某道题写得特别不规范，我是整份报错停下来的，其实可以改成就跳过并警告。
